## Business-visible outcome

The business can switch the Public Website to the alternate `ocean` theme with automated proof that content, layout behaviour and accessibility are unchanged.

## In scope

- **Enumerate the delivered public routes** from the application itself and record the exact list covered.
- **Parity spec** `tests/e2e/theme-parity.spec.ts`: for each route, capture a structural snapshot under `carchief` and under `ocean` and assert they are identical. Compare DOM structure, element order, roles, accessible names, headings, link targets and visible text — never colour values. Run it across the `chromium`, `mobile-chromium` and `tablet-chromium` projects.
- Assert `data-theme` on `<html>` matches the configured theme, and that an unknown `NEXT_PUBLIC_THEME_ID` falls back to `carchief`.
- Assert that token-derived custom properties on `<body>` do differ between the themes, so a no-op configuration cannot pass as parity.
- **Contrast tests** `packages/theme/src/__tests__/theme-contrast.test.ts`: every semantic foreground/background pairing in both themes meets the required contrast ratio, using the existing helpers in `packages/theme/src/contrast.ts`. Assert both themes define every token in `SemanticThemeTokens`, with no missing token relying on a component fallback.
- Record any parity failure as a finding with the owning task and route; **do not** fix a feature component here.
