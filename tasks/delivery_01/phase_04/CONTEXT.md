# Phase 1.4 Context Pack — Vehicle details

Read this file first. It carries the requirement text, decisions, code map and conventions the Phase 1.4 tasks need, so `REQUIREMENT.md` and `FRONT_END_ARCHITECTURE.md` only need to be opened for an item this pack marks unresolved.

Authority order is unchanged: `REQUIREMENT.md` → `FRONT_END_ARCHITECTURE.md` → `docs/CarChief-Frontend-Implementation-plan.md` §5 Phase 1.4 → roadmap → decisions → evidence. `POC/**` is conceptual reference only.

## 1. Requirements in scope (verbatim from `REQUIREMENT.md`)

**PUB-09** Each vehicle has its own page showing photos, specifications, and price.

**PUB-10** A vehicle's page can be shared as a single link that opens directly to that vehicle, from a fresh browser with nothing pre-loaded.

**PUB-11** Each vehicle's page carries its own title and description, so it can be found and shared properly through search engines and social media.

**PUB-25 — Source-confirmed by legacy public-site audit:** A visitor can browse only the approved public stock categories (for example, arrival, premium or clearance) and country-specific stock projections. Category, country eligibility, operational status, commercial state, publication and price readiness remain distinct server-authoritative concepts.

**PUB-28 — Source-confirmed contact pattern:** A visitor can use approved public contact actions, including vehicle/general enquiry and clearly labelled WhatsApp, email or call intent. The site must not claim a message, call, notification or external hand-off completed unless an approved service confirms it.

**RULE-08** Whenever something is saved, edited, or deleted anywhere in the system, that change is reflected immediately and consistently everywhere it is shown. A save or delete must never appear to succeed while quietly not taking effect, and it must never take effect while the screen shows the old information as if nothing happened.

**RULE-10** The system never claims a capability it does not actually have. If a message tells the user something is happening automatically, securely, or successfully, that must be true.

| `DEC-WF-PUBLICATION-PRICE` | RESOLVED | `Active` and `Now On Sale` are separate fields. A price request creates a normal lead. Country price readiness is an approved service projection — never manufacture a price for price-request stock. |

| `DEC-PUB-PREMIUM-STOCK` | OPEN | Premium eligibility and WhatsApp behaviour are unconfirmed. WhatsApp stays clearly labelled *contact intent*; never claim delivery (RULE-10). |

## 5. Known pitfalls already paid for in earlier phases

- **CORS**: any new mock route reached from the browser needs the existing CORS middleware in `apps/mock-api/src/server.ts` to remain in front of it. Phase 1.3 lost time to this.
- **Playwright strict mode**: a locator matching more than one element fails. Prefer `getByRole` with an accessible name, or scope to a test id on the container.
- **Docker schema drift**: `CREATE TABLE IF NOT EXISTS` does not add columns to an existing table. If a new column is added to the `vehicles` table, the local Compose volume must be recreated — see `DEVELOPER_USER_GUIDE.md`.
- **Vitest name filters**: run tests by explicit path. A name filter that matches nothing exits non-zero and looks like a failure.

## 6. Boundaries

- Features never import `api-client/generated/**` or `http.ts`; routes never import services directly; `packages/ui` never imports a service. `corepack pnpm test:boundaries` enforces this.
- No app imports `apps/mock-api`, Prisma, Firebase, Firestore or Supabase.
- Never expose `internalNotes`, `staffOwnerId` or any unpublished media field in a public response.
- Authorization, workflow transitions, integrity validation and authoritative calculations stay server-side.
- Do not modify `POC/**`; `git diff -- POC` must stay empty.
