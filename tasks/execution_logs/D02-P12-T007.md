## Blocker found during required-reading verification (before implementation)

Reading list item 11 required reading all five preceding execution logs. `tasks/execution_logs/D02-P12-T006.md` ("AI code review" → "finding 2" and its "Decisions and deviations") already documents that `GET /api/v1/customer/profile` **404s for a freshly `POST /api/v1/auth/register`-ed account**, because `registerCustomerAccount` (both `MemoryStore` and `PostgresStore`, `apps/mock-api/src/store.ts`) never creates a `CustomerProfile` record — only the seeded fixture customer (`cust-123`) has one. T006 explicitly recommended: *"the phase owner add one (or extend D02-ASM-005) if a future task is meant to close it via a `D02-P12-T001`-owned Mock API change."*

T007 is that future task. This task's file requires, as the primary in-scope deliverable and acceptance criterion:

> "register in public-web → forward to Customer sign-in → sign in → **open profile → change password** → sign out → sign in with the new password → forgot password → reset via the non-production outbox → sign in with the reset password."

and

> "The full register → sign in → change password → forgot password → reset → sign in journey passes against a fresh Docker runtime at all three viewports."

This is a **freshly registered account**, not the seeded fixture — the whole point of the spec is to prove self-registration works end to end. I reproduced the gap empirically before writing any test, against a locally built Profile-A mock-api (`node apps/mock-api/dist/server.js`, port 4000, `NODE_ENV=development`):

```
POST /api/v1/auth/register  {"nameWithInitials":"J. Repro", "countryCode":"KE", "mobileNumber":"712345678",
                              "email":"repro-<ts>@example.com","password":"Sup3rSecretPass1","confirmPassword":"Sup3rSecretPass1"}
→ 201 {"id":"acct-...","customerId":"cust-1786848559315-io59cc", ...}

POST /api/v1/auth/login     {"email":"repro-<ts>@example.com","password":"Sup3rSecretPass1"}
→ 200 {"token":"...","claims":{"sub":"cust-1786848559315-io59cc", ...}}

GET  /api/v1/customer/profile   Authorization: Bearer <token>
→ 404 {"statusCode":404,"message":"Customer profile not found","correlationId":"corr-404-..."}
```

Traced the cause to `apps/mock-api/src/server.ts:499-505` (`GET /api/v1/customer/profile`), which 404s whenever `store.getCustomerProfile` throws (both stores throw when no `CustomerProfile` row exists for the customer id), combined with `apps/customer-app/src/features/profile/ProfilePage.tsx:220` gating the entire authenticated body — including the "Change password" form — behind `!profileQuery.isLoading && !profileQuery.error && profileQuery.data`. For a freshly registered account, `profileQuery.error` is always set, so **the Change-password form never renders**, and the journey this task must prove cannot be completed against a real self-registered account, only against the pre-seeded fixture identity.
