### Defect found: literal (non-token) colours across four stylesheets ignored the active theme

The MCP walkthrough of the `ocean` pass showed the home hero, header/footer chrome, and the `public-content` / `faq` / `testimonials` feature pages rendering **visually identical to `carchief`** (still red/orange/black) despite the server being started with `NEXT_PUBLIC_THEME_ID=ocean` and `data-theme="ocean"` being correctly set on `<html>`. Source inspection found the root cause in each owned file:

- `apps/public-web/src/app/globals.css` — the home hero (`.hero`, `.hero-eyebrow`, `.hero-title`, `.hero-title-accent`, `.hero-subtitle`, `.hero-btn-primary`(`:hover`), `.hero-btn-secondary`(`:hover`), `.hero-value-strip`, `.value-strip-title`, `.value-strip-text`), the header/nav (`.header-shell`, `.brand-icon`, `.brand-name`, `.nav-link`(`:hover`), `.nav-link-active`, `.mobile-menu-toggle`, `.mobile-nav-drawer`, `.mobile-nav-link`) and the footer (`.footer-shell`, `.footer-tagline`, `.footer-description`, `.footer-links-col h4`/`a`(`:hover`), `.footer-security-text`, `.footer-bottom`) declared hard-coded hex/`rgba()` literals (comments literally read "POC Dark Photographic Theme" / "POC Dark Theme Navigation" / "POC Dark Theme Footer") instead of the semantic `var(--color-*)` custom properties `layout.tsx` applies to `<body>`.
- `apps/public-web/src/features/public-content/public-content.css`, `apps/public-web/src/features/faq/faq.css`, `apps/public-web/src/features/testimonials/testimonials.css` — a **more severe** variant of the same defect: these three files reference CSS custom properties in the form `var(--cc-color-text-primary, #ffffff)`, `var(--cc-color-accent, #ff4d4d)`, etc. The `--cc-*` custom-property names are **never defined anywhere in the codebase** (confirmed by `grep -rn "^\s*--cc-" apps/ packages/` — zero matches); `layout.tsx` only ever sets the real `--color-*`/`--spacing-*`/etc. names from `packages/theme/src/provider.ts`. Every one of these `var(--cc-*, <fallback>)` declarations therefore **always** resolves to its hard-coded fallback, on both themes, permanently — the fallback is not a fallback, it is the only value that has ever applied. This affected the shared `ContentPageTemplate`/`ContactPageContent`/`BranchPageContent`/`PrivacyPageContent` components (routes `/about`, `/services`, `/how-to-buy`, `/auction`, `/branches`, `/branches/[branch]`, `/shipping-schedule`, `/privacy`, `/content/[slug]`, `/contact`), plus `/faq` and `/testimonials` — roughly 13 of the 17 delivered routes.
- The already-correct parts of the codebase (`apps/public-web/src/features/home/home.css`, `packages/vehicle-search/src/vehicle-search.css`, `packages/vehicle-detail/src/vehicle-detail.css`, `apps/public-web/src/features/vehicle-detail/vehicle-detail.css`) were read and confirmed clean (0 literal-colour / 0 fake-token occurrences) and used as the reference convention for the fix: real tokens with no fallback, and `color-mix(in srgb, var(--color-text-on-dark) N%, transparent)` for a themed translucent tint — this exact `color-mix` idiom is already established in `public-content.css` lines 313–343 (untouched) and in `vehicle-detail.css`'s own header comment ("No literal colours, no fallback palettes: a fallback would silently pin the default `carchief` palette and mask a mistyped token name").

**Fix applied** (token values and stylesheet ownership only, per scope):

1. **`packages/theme/src/tokens.ts` / `registry.ts` / `provider.ts`** — added one new semantic colour token, `colors.accent`, because the hero/nav/footer literals used a distinct brand orange (`#ea580c`) with no existing token match (`primary`/`primaryHover`/`secondary` are all different hues/values). `carchief.accent = '#ea580c'` — **the exact literal already in production**, so `carchief` has zero value drift. `ocean.accent = '#0e7490'` (a cyan in the ocean blue/teal family), chosen so `textOnPrimary`-on-`accent` (the button/pill background use, the more frequent and more business-critical of the token's two usage patterns — primary CTA buttons across the hero and all three feature stylesheets) is comfortably WCAG AA (5.36:1, verified with the project's own contrast formula reimplemented in a throwaway script, then cross-checked against `packages/theme/src/contrast.ts`'s real output via the Vitest run below). `getThemeCssVariables` now emits `--color-accent`. `packages/theme/src/__tests__/theme.test.ts`'s hard-coded `expect(Object.keys(vars)).toHaveLength(49)` was updated to `50` — a one-line, mechanical, unavoidable consequence of the token addition, inside the `packages/theme/src/**` owned path; no other assertion in that file was touched.
2. **`apps/public-web/src/app/globals.css`** — every hero/nav/footer literal listed above replaced with `var(--color-*)` (direct token reuse) or `color-mix(in srgb, var(--color-text-on-dark|primary|accent) N%, transparent|var(--color-surface-dark))` (for translucent tints, borders and muted text — the same idiom already established elsewhere in this codebase), each mix percentage back-solved from the literal it replaces so `carchief`'s rendering is unchanged (verified visually below). `.online-badge`/`.online-dot` (status "online" green) and `.footer-envelope-badge` (security/trust red) were deliberately **left as literals** — they are status/security indicators, not brand colour, and both existing status tokens (`success`/`warning`/`error`/`info` and their `*Surface` companions) are **already identical across both themes in `packages/theme/src/registry.ts`**, so touching them would have had zero effect on ocean parity while adding risk.
3. **`apps/public-web/src/features/public-content/public-content.css`, `faq.css`, `testimonials.css`** — every `var(--cc-color-*, <fallback>)` and matching plain literal mapped to the real token whose role it actually plays (e.g. `--cc-color-text-primary`→`--color-text-on-dark`, `--cc-color-bg-dark`→`--color-surface-dark`, `--cc-color-border`→a `color-mix` border-on-dark, `--cc-color-accent`/`--cc-color-button-bg`→`--color-accent` or `--color-primary` depending on which the original literal's RGB value was actually closest to — `faq.css`'s `#da3633`/`#b82a28` button colours are near-exact matches for `primary`/`primaryHover`, not `accent`, so they were mapped to `primary`/`primaryHover`). `.cc-btn--whatsapp`'s literal WhatsApp green was mapped to `var(--color-success)`, following the **exact existing precedent** already in `home.css`'s `.whatsapp-link { color: var(--color-success); }`. Amber/warning badge literals (`--cc-color-accent-amber, #d97706` in `faq.css`) and every success/warning/error alert literal were deliberately **left untouched** for the same status-token-is-already-theme-invariant reason as above — mapping them to `--color-warning` (`#92400e`, calibrated for light `warningSurface` backgrounds) would have made them il­legible against these pages' dark backgrounds while producing zero parity benefit. `--cc-space-*` (spacing) fake-token references were deliberately **left untouched**: `spacing`/`radii`/`shadows`/`typography`/`motion` tokens are shared, identical objects across both themes in `registry.ts` (`spacing: defaultSemanticTheme.spacing`, etc.), so no spacing/radius/shadow literal can ever cause an ocean-parity defect — fixing them would have been a large, unrelated stylesheet-hygiene sweep outside this task's "fix parity defects" charter (`tasks/delivery_01/phase_09/D01-P09-T002.md` "In scope"/"Explicitly excluded").
