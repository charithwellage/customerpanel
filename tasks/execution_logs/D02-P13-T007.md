## Fix pass — 2026-08-18 (Finding 3 closure)

### Root causes found and fixed

1. `signIn()` in both `wishlist.spec.ts` and `favourites.spec.ts` waited on `page.getByRole('heading', { name: 'Customer Portal' })`, which does not exist in the rendered shell. Fixed to `page.waitForSelector('.cc-cust-shell-layout', ...)`, the real always-present shell wrapper.
2. `wishlist.spec.ts`'s "displays wishlist after adding a vehicle" test used `page.getByTestId('add-to-wishlist-btn')`, a testid that does not exist anywhere in the codebase; the real button (T005) is `data-testid="wishlist-toggle-btn"`. The vehicle was silently never wishlisted.
3. `favourites.spec.ts`'s `page.getByLabel(/Model/)` matched two form fields ("Model" and "Model Code") and threw a Playwright strict-mode violation; narrowed to `/^Model$/`.
4. Both specs shared one fixture account (`demo.customer@carchief.com`) plus a global `POST /api/v1/__reset` `beforeEach` (the `profile.spec.ts` precedent). This is unsafe here specifically: with the three viewport projects running concurrently under `--workers=50%`, one project's reset wiped another project's just-added wishlist item/favourite moments before its own assertion ran — observed directly as an intermittent "no items" failure on an otherwise-correct flow, reproducing on different projects across repeated runs. Neither wishlist nor favourites data depends on a seeded profile field, so both specs now register a fresh, uniquely emailed account per test via `POST /api/v1/auth/register` (the `account-access.spec.ts` precedent) instead — no shared state, no reset, immune to cross-project races.
5. Also replaced two structurally-empty favourites tests (which only asserted `if (count > 0) {...}` against an always-empty account, i.e. asserted nothing) with one real test that creates a favourite through the UI and verifies it renders with the expected name/criteria/date — genuine coverage instead of a vacuous conditional.
