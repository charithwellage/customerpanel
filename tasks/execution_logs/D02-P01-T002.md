### Findings closed by this task

- **Finding 3 (shared with T001) — fabricated identity.** `accountState.ts`'s `createDemoCustomerSession`
  previously hardcoded `Charles Sterling` / `c.sterling@sterlingimports.com` / `Sterling Imports Ltd` and
  ignored `response.claims` entirely, while the Mock API actually mints `sub: 'user-123'`,
  `email: 'user@carchief.com'` via `createDemoJwtToken('CustomerBuyer')`. It now derives every field from the
  response: `id` from `claims.sub`, `email` from `claims.email`, `role`/`permissions`/`expiresAt` from the
  matching claims. Because `JwtClaims` carries **no `name` and no `company` field**, a display name cannot be
  read honestly from the token, so a documented helper `deriveCustomerDisplayName` takes the local part of the
  verified address and falls back to the exported `DEMO_CUSTOMER_DISPLAY_NAME` (`Demo Customer`) when no
  address is present. `company` is now left `undefined` rather than invented.
- **Finding 3 (continued) — pre-filled fake credentials.** `LoginForm.tsx` no longer seeds state with the
  fabricated address and a dot-filled password that made the form look like someone was already signed in.
  Both fields start empty and the example address moved to a `placeholder` attribute, which is not a value.
- **Finding 4 (shared with T001) — false Keycloak claim.** `AccountStateBanner.tsx`'s LOCKED copy no longer
  tells the user to "complete Keycloak recovery process". It now reads "Security lock applied. Account
  unlocking is handled by AutoPulse identity operations and is not available in this demo build.", matching
  the honest boundary tone already used correctly in `PasswordRecoveryCard.tsx`.
- **Finding 2 (shared with T001/T003) — invalid browser evidence.** Rewrote
  `tests/e2e/customer/account-access.spec.ts`, which previously asserted only that `main` and `body` were
  visible — assertions that pass against any page on any port. It now asserts the "CUSTOMER PORTAL ACCESS"
  badge, the "Sign In to CarChief" heading, the `cust-login-email`/`cust-login-password` fields being present
  **and empty**, the absence of any "Sterling" string, label/keyboard reachability, the "Forgot Password?"
  route into the identity-boundary card, and a real browser-to-mock sign-in asserting
  `POST /api/v1/auth/demo-session` returns 201 and the page then shows the genuine `user@carchief.com`.
  **Counter-check:** aimed at `public-web` (port 3000) these specs now fail 6/6, so they can no longer pass
  against the wrong target. Genuine fresh-runtime evidence is recorded below.
- **Finding 5 (non-blocking).** `LoginForm` field ids now come from `useId()` instead of the fixed
  `cust-login-email`/`cust-login-password`. Those names are preserved as `data-testid` values so the browser
  specs keep stable, meaningful selectors without reintroducing colliding DOM ids.

### Additional in-scope defects found and fixed during this pass

1. **Browser-only validation blocked the only sign-in path (introduced-visibility, blocking).** Both credential
   inputs carried `required`. With the fabricated pre-fill removed the fields are legitimately empty, so HTML5
   validation silently blocked submission and **no API call fired at all** — the sign-in journey was dead. The
   demo-session endpoint ignores the credentials entirely, so enforcing them in the browser was validation with
   no server counterpart: exactly the "browser-only validation" defect `TASK_EXECUTION_PROTOCOL.md` §7
   prohibits. Removed `required` from both fields, relabelled the submit control from
   "Sign In / Request Demo Session 🚀" to "Request Demo Session 🚀" (which is what actually happens), and made
   the footer note state plainly that the address and password "are not verified and are not transmitted" and
   that production credential sign-in belongs to AutoPulse. A regression test locks this in.
2. **Recovery surface layout (found by the MCP walkthrough).** `AccountGuard` returned `PasswordRecoveryCard`
   without the `cc-acc-guard-surface` wrapper that its login and account-state branches use, so the card
   rendered flush against the viewport edge. Wrapped it to match; re-built, restarted and re-walked.
3. **`AccountGuard` could not pass the verified session to its children,** so the shell had no way to display
   the identity the Mock API returned — the root cause that made the fabricated default visible in the first
   place. `children` now accepts either `ReactNode` or `(session: CustomerSession) => ReactNode`
   (`AccountGuardChildren`); the existing `ReactNode` form is unchanged, so no existing caller or test breaks.
4. **Account feature stylesheet was missing entirely.** Every `cc-acc-*` class referenced by this feature's
   components existed in no stylesheet, so the login card, banner and recovery card rendered unstyled. Added
   `apps/customer-app/src/features/account/account.css`, written only from `packages/theme` semantic tokens.
