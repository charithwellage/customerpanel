### The `VITE_API_BASE_URL` / container-networking decision

`VITE_*` variables are inlined into the static bundle at **build** time, and that bundle executes in the
**host browser**, not inside the Compose network. Baking `VITE_API_BASE_URL=http://mock-api:4000` would
therefore produce a URL the browser cannot resolve, and baking `http://127.0.0.1:4000` would hard-code a
host-specific origin into an image and break whenever `CARCHIEF_MOCK_API_PORT` is overridden.

The chosen design defers the URL to same-origin relative fetches:

- `VITE_API_BASE_URL` is left **unset**, so `apiBaseUrl` is `''` and the browser calls `/api/v1/*` on the
  customer app's own origin. This matches how `public-web` already works — its browser traffic goes through
  `src/app/api/v1/[...path]/route.ts` rather than straight to the mock.
- `vite.config.ts` proxies `/api/v1` to `CUSTOMER_API_PROXY_TARGET` (default `http://127.0.0.1:4000`) in both
  the dev and preview servers. That value is read at **start** time by the Node process serving the bundle, so
  Compose can safely set it to the internal `http://mock-api:4000`; nothing container-internal ever reaches the
  browser.
- An explicit `VITE_API_BASE_URL` is still honoured for the case where the API genuinely is reachable from the
  browser at that exact origin (the Mock API sends `Access-Control-Allow-Origin: *`), and `.env.example` warns
  against pointing it at a container hostname.

Verified in the live runtime: `curl -X POST http://127.0.0.1:3001/api/v1/auth/demo-session` returned **201**
through the customer app's own origin, and the browser sign-in journey issues that same same-origin request.
