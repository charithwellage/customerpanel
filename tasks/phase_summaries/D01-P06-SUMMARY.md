# Phase 06 Summary: Enquiry, Account and Reservation Entry

## Overview
Phase 1.6 delivers the public lead/enquiry capture, the stand-in demo account entry point, and the transactional vehicle reservation journey, on `feat_delivery01_phase_06`. A visitor can contact CarChief (general or vehicle-specific), start account access via a non-production demo identity (`DEC-PUB-AUTH-BOUNDARY`), and — once signed in — request an eligible reservation with a durable, staff-visible record, all with honest eligibility/conflict/limit/expiry feedback and no fabricated notification/automatic-release claim (RULE-08, RULE-09, RULE-10).

## Key Deliverables Completed
- **D01-P06-T001** — Lead/enquiry contract extension: `enquiryType`/`source` vocabularies, the canonical staff-visible `LeadRecord`/`LeadListResponse`, and `GET /api/v1/enquiries`/`GET /api/v1/enquiries/:id` gated to the `Salesperson` role — the explicit fix for the POC's disconnected-lead defect (a submitted enquiry is now retrievable through the staff-facing boundary).
- **D01-P06-T002** — Accessible contact and vehicle enquiry forms: a required consent checkbox, preferred-contact-method selection, optional vehicle-preference fields, and `react-hook-form`/Zod validation (`packages/validation`) mirroring the mock's own server-authoritative checks.
- **D01-P06-T003** — Account entry and unauthenticated reservation guidance: `POST /api/v1/auth/demo-session` (always mints a `CustomerBuyer` identity, never a caller-supplied role), the `/account` route, header/nav sign-in trigger, and `ReservationSignInGuidance` — built and proven as a reusable component, ready for `D01-P06-T005` to embed.
- **D01-P06-T004** — Transactional reservation eligibility and hold: `POST /api/v1/reservations`/`GET /api/v1/reservations/:id`, a 48-hour hold (RULE-05), concurrency-safe eligibility (conflict/duplicate/vehicle-unavailable/limit-exceeded via a flat, documented anti-abuse ceiling — `D01-ASM-003`), and a live-recomputed `expired`/`active` status that never claims an automatic release (`DEC-PUB-RESERVATION-EXPIRY-ACTION` stays `OPEN`).
- **D01-P06-T005** — Reserve action UI wired into the vehicle detail page: composes `T003`'s `ReservationSignInGuidance`/`useSession` with `T004`'s `ReservationService` (new `features/reservation/` slice — `useReservation`, `ReservationAction`, `ReservationUnavailableNotice`); an honest RULE-09 empty state for a non-reservable vehicle status; success/expiry/conflict/limit feedback backed by the mock's own reviewed error messages; and a fresh-page-reload proof that a created reservation is retrieved through the service boundary, not local state alone. Also fixed a previously-latent gap in the same-origin browser-to-mock proxy (`src/app/api/v1/[...path]/route.ts`), which dropped the `Authorization` header before this task's first authenticated browser call needed it.
