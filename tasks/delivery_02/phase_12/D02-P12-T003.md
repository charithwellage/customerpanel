## Business-visible outcome

A visitor sees Login and Register in the site header, and Register leads to a working self-service account creation form.

## In scope

- `apps/public-web/src/shell/HeaderComponent.tsx`: delete `AccountEntryTrigger` and its `CUSTOMER PORTAL`/`DEMO ACCOUNT` labels. Render a **Login** secondary action and a **Register** primary action inside `.header-actions`, and repeat both at the end of `.mobile-nav-drawer`.
- **Login** navigates to the Customer application sign-in entry point resolved from configuration, never a hard-coded host. **Register** navigates to `/register`.
- New route `apps/public-web/src/app/register/page.tsx` plus `apps/public-web/src/features/registration/` holding the form, its hook and its stylesheet.
- The form collects exactly: name with initials, country (select), mobile number, email address, password and re-entered password. Selecting a country sets and displays that country's dial code next to the mobile-number input; changing the country updates the dial code.
- Submit calls `AuthService.register`. Success does **not** create a session: it presents a confirmation and forwards the visitor to the Customer application sign-in with the registered email pre-filled, so no token crosses an origin boundary.
- Server `field` errors attach to the matching input; the duplicate-email 409 renders on the email field.
- Add `/register` to the sitemap/robots handling consistent with the existing `/account` route metadata, and mark it `noindex` only if the existing account layout precedent requires it.

## Contract and incremental mock work

No Mock API or OpenAPI change is owned. Consume `AuthService.register` and `CountryService` from `D02-P12-T002`.

### Frontend API integration

The country list is fetched through `CountryService` on the client and rendered from the response; it is never hard-coded in the component. Registration posts through `AuthService.register` via the `src/app/api/v1/[...path]/route.ts` proxy, so the browser never talks to the Mock API origin directly. Render explicit loading, validation, duplicate-email, network-error and success states.

## Implementation and UX requirements

- Read and follow [COMMON_FRONTEND_RULES.md](../../COMMON_FRONTEND_RULES.md).
- Support 390x844, 768x1024 and 1440x900, full keyboard operation, visible focus, contrast and reduced motion.
- Every input has a persistent visible label, an `autocomplete` attribute (`name`, `tel`, `email`, `new-password`) and an `aria-describedby` error association.
- Password and re-entered password are `type="password"` with an accessible show/hide control; neither value is ever placed in a URL, a query string or the browser history.
- The submit control is disabled while in flight and the form is not resubmittable by a double click.
- Errors are announced to assistive technology through a live region as well as inline.
