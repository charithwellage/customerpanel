## Requirements and rules

**Delivery 02 execution policy:** Run the task-owned tests and dependency-closure build named under **Validation commands**. Do not edit another task's owned paths.

**Phase 2.13 identity policy.** `customerId` on an enquiry is resolved server-side only, through `resolveCustomerScope(req.user.sub)`, exactly as Phase 2.12 resolves customer scope for reservations. It is never accepted as a field on the request body; a client-supplied `customerId` is ignored, not trusted. Anonymous (public-web, unauthenticated) submissions continue to work exactly as before — `customerId` is simply absent on those rows.

A quote request is never blocked as a duplicate. The existing dedupe mechanism in `prepareEnquiry()`/`buildEnquiryDedupeKey()` collapses a byte-identical resubmission into an updated `duplicateResubmissionCount` on the same row and returns `200 duplicate:true`; it must keep doing exactly that, now keyed so two different customers sharing an email are never incorrectly collapsed into one row.

## Business-visible outcome

A signed-in customer's quote requests are attributable to them, a customer can later retrieve the list of vehicles they requested a quote for, and anyone can see how many distinct people have requested a quote for a given vehicle.

## In scope

- `packages/domain/src/index.ts`: add `customerId?: string` to `EnquiryRequest` (documented as server-populated only, never client-supplied) and to `EnquiryResponse`; add `CustomerInquirySummary { vehicleSlug, vehicleId, vehicleTitle, requestedAt, inquirerCount }`, `CustomerInquiryListResponse { items: CustomerInquirySummary[] }`, and `VehicleInquiryAggregate { vehicleSlug, inquirerCount }`.
- `apps/mock-api/src/store.ts`:
  - `EnquiryRecord` gains `customerId?: string`.
  - `prepareEnquiry()` accepts an optional trusted `customerId` supplied by the route handler (never read from the request body); `createEnquiry()` in both `MemoryStore` and `PostgresStore` persists it.
  - `buildEnquiryDedupeKey()` keys off `customerId ?? email` (plus the existing vehicle/destination/type/message components) so authenticated and anonymous submitters are never conflated.
  - New `DemoStore` interface methods, implemented in both stores: `listCustomerInquiries(customerId: string): CustomerInquirySummary[]` (one row per distinct vehicle the customer has an `enquiryType: 'price-request'` enquiry for, each carrying that vehicle's current aggregate count) and `getVehicleInquiryAggregate(vehicleSlugOrId: string): VehicleInquiryAggregate` (counts distinct `customerId ?? email` among `enquiryType === 'price-request'` rows for that vehicle; 0 if the vehicle exists but has no quote requests).
  - Postgres schema: `ALTER TABLE enquiries ADD COLUMN IF NOT EXISTS customer_id text;` immediately after the existing `enquiries` table block, following the documented precedent for adding a column to an existing volume.
  - `reset()` in both stores continues to clear all enquiry rows, including the new column, with no special-casing.
- `apps/mock-api/src/server.ts`:
  - `POST /api/v1/enquiries`: when `req.user` is present, resolve `resolveCustomerScope(req.user.sub)` and pass it through as the trusted `customerId`; when absent, behavior is unchanged from today.
  - New `GET /api/v1/customer/inquiries` — requires `req.user`; 401 if absent; returns `CustomerInquiryListResponse` for `resolveCustomerScope(req.user.sub)`.
  - New `GET /api/v1/vehicles/{idOrSlug}/inquiry-count` — public, no authentication required; 404 if the vehicle does not exist; returns `VehicleInquiryAggregate`.
