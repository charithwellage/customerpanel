## Requirements and rules

**Delivery 02 execution policy:** Run the task-owned tests and dependency-closure build named under **Validation commands**. Do not edit another task's owned paths.

Every Favourites dropdown option comes only from `FavouritesService.getFacets()` — never a hardcoded list. Per `D02-ASM-008`, the Model Code, Engine CC, Color and Steering dropdowns render visibly disabled with a "no data yet" state, because the facets response returns empty arrays for those four fields; this is an honest unavailable state, not a bug to work around with fabricated options. The 25-favourite cap is enforced authoritatively by the Mock API (T002); this task adds client-side UX (disable the create action, show a clear message) on top of that, and must never claim success on a create the server rejected.

## Business-visible outcome

A signed-in customer can view and manage a wishlist of specific vehicles, and can create, view and delete up to 25 saved search-criteria favourites, with every favourite dropdown reflecting real inventory data.

## In scope

- New `apps/customer-app/src/features/wishlist/`: `CustomerWishlistPage.tsx` (list with a remove action per item, calling `WishlistService.remove`), `useCustomerWishlist.ts` (`WishlistService.list()`), `wishlist.css`, `__tests__/wishlist.test.ts`, `index.ts`. Empty state with a link back to inventory browsing.
- New `apps/customer-app/src/features/favourites/`: `CustomerFavouritesPage.tsx` (list of existing favourites with a delete action, plus a "Create favourite" trigger), `FavouriteSearchForm.tsx` (name field plus all fourteen criteria dropdowns, each populated from `FavouritesService.getFacets()`; the four unbacked fields — Model Code, Engine CC, Color, Steering — render disabled with a "no data yet" label per `D02-ASM-008`), `useCustomerFavourites.ts` (`FavouritesService.list()`/`.create()`/`.remove()`/`.getFacets()`, plus a client-side check that disables the create action and shows "You have reached the 25-favourite limit" at 25 existing favourites — this is UX only; the actual rejection is server-side per T002), `favourites.css`, `__tests__/favourites.test.ts`, `index.ts`.
- `apps/customer-app/src/app/App.tsx`: add `/wishlist` and `/favourites` branches following the existing pattern.
- `apps/customer-app/src/features/shell/CustomerShellProvider.tsx`: add `{ id: 'wishlist', label: 'My Wishlist', href: '/wishlist', icon: '❤️' }` and `{ id: 'favourites', label: 'Favourites', href: '/favourites', icon: '⭐' }` to `DEFAULT_NAV_ITEMS`.
- `apps/customer-app/src/features/registry/featureRegistry.ts`: add `wishlist` and `favourites` entries, keeping the registry's uniqueness validator green.

## Contract and incremental mock work

No Mock API or OpenAPI change is owned. Consume `WishlistService` and `FavouritesService` from `D02-P13-T003`.

### Frontend API integration

Both pages fetch and mutate through their respective services and `HttpClient`, never a hand-built fetch or a fixture. The Favourites form's dropdown options are populated exclusively from the `getFacets()` response on every render — no field's option list is ever hardcoded in the component. Render explicit loading, empty, at-cap, validation (server 400 on empty criteria, mapped to a form error) and success states for Favourites, and loading/empty/success for Wishlist.

## Implementation and UX requirements

- Read and follow [COMMON_FRONTEND_RULES.md](../../COMMON_FRONTEND_RULES.md).
